# Dashboard: ส่วนที่เพิ่มตาม requirement

ปรับปรุงวันที่ 14 กันยายน 2569 ใน `Graph_RAG/frontend` บน branch `codex/dashboard-web-integration`

ขอบเขตงานคือ Dashboard mock ในเว็บ NextLink สำหรับเจ้าหน้าที่ ใช้ชุดข้อมูลสมมติและบันทึกในเบราว์เซอร์แยกตามบัญชี ยังไม่เชื่อมฐานข้อมูลธุรกิจจริงหรือ CRM API และไม่รวม Planner / NextPlus

## สิ่งที่ตรวจได้จากหน้าเว็บ

| หน้า | ส่วนที่เพิ่ม | วิธีทดลอง |

| ฝึกงาน / สหกิจ | ตัวกรองชั้นปีและรอบ; Top 10 บริษัท/ตำแหน่ง; รองรับอันดับย้อนหลังถึง 10; ผลประเมินย้อนหลัง; เปิด Case รายบริษัท | ฝึกงานปี 2566 ภาคฤดูร้อนมีตัวอย่างอันดับ 1–10; เลือกชั้นปี/รอบและเปิดรายละเอียดบริษัท |

## ความหมายและข้อจำกัดของข้อมูล

- แหล่งอ้างอิงคือ requirement และเอกสารที่ตรวจไว้ใน parent workspace: `docs/audits/dashboard-requirements-2026-09-14/report.md` และ `docs/audits/dashboard-drive-recheck-2026-09-14/report.md` ไม่ได้นำรายชื่อนิสิตหรือข้อมูลติดต่อจริงจาก Drive มาใส่ใน fixture
- ทะเบียนบริษัทจับคู่โมดูลด้วยรหัสที่กำหนดชัดเจนสำหรับ fixture เท่านั้น บริษัทที่ชื่อคล้ายกันไม่ถูกควบรวมอัตโนมัติ ชื่อจากแต่ละชุดแสดงเป็น alias ตัวอย่าง
- ผู้ติดต่อในทะเบียนเป็นข้อมูลร่วมของ demo ส่วนชื่อผู้ประสานงานเดิมในแถว MOU/วิชาเลือก/โครงการยังเป็นข้อมูลประจำเอกสารหรือรายการนั้น ไม่ใช่การซิงก์กลับ CRM จริง
- Case เก็บวันที่เกิดเหตุ ปี/เทอม วันที่บันทึก ผู้บันทึก โมดูล รายละเอียด และสถานะ เรียง Case ล่าสุดตามวันที่เกิดเหตุ รองรับการบันทึกเหตุการณ์เก่าภายหลัง ประวัติในเบราว์เซอร์ยังไม่ใช่ audit log ที่ยืนยันจากเซิร์ฟเวอร์
- อันดับฝึกงานนับทุกอันดับบวกที่มีข้อมูล ไม่จำกัดแค่ 1–5 และแยกตำแหน่งด้วย Opening ID; ชื่อซ้ำที่ระบุไม่ได้จะไม่ถูกเดารวมกัน
- ตัวเลขรับแยกชั้นปี/รอบเป็นการแบ่งจำนวนใน fixture แบบไม่ซ้ำและผลรวมเท่าเดิม ไม่ใช่กฎโควตาจริง เมื่อกรองชั้นปี/รอบจะปิดการแก้ยอดรวม เพื่อไม่ให้บันทึกยอดบางส่วนทับยอดทั้งเทอม
- ผลประเมินฝึกงานเป็นนิสิตประเมินบริษัทในชุดสมมติ แยกจากคะแนนที่บริษัทประเมินนิสิต คำตอบว่างไม่เท่ากับศูนย์ ข้อมูลสหกิจยังต้องยืนยัน requirement และตัวอย่างเฉพาะโมดูลก่อนเชื่อมระบบจริง
- รายการ MOU ที่ไม่พบ Friday ใช้สถานะเอกสารเทอม 1/2569 และกิจกรรม `completed` ทุกเทอมใน fixture ปี 2566–2569 ไม่ใช้ตัวกรองรายการกิจกรรมมาจำกัดประวัติ และไม่สรุปหากข้อมูลบางส่วนอ่านไม่ได้ คำว่า “ไม่พบ” ไม่ใช่การรับรองว่าบริษัทไม่เคยเข้าร่วมในประวัติจริงทั้งหมด
- รูปแบบต้นทาง `Hackatron` จับคู่เป็น Hackathon โดยรักษาข้อความต้นทางไว้ ค่าว่างและรูปแบบที่ไม่รู้จักยังแยกจากกัน ผลประเมินบริษัทคงเป็นข้อความสามด้าน
- Milestone ต้องมีชื่อ วันที่จริงในปฏิทิน สถานะที่รองรับ และอ้างถึงทีมที่ยืนยันแล้ว การลบยังทิ้งประวัติก่อน–หลังไว้
- การเชื่อมบัญชีบริษัท/ผู้ติดต่อจริง การนำเข้าเอกสาร ผลประเมินจริง และการบันทึกลง Database v1 ยังเป็นขั้นตอนถัดไป

## การตรวจสอบ

- `npm run check:dashboard` — 68 domain tests ครอบคลุมอันดับ 1–10, Opening ID ซ้ำชื่อ, ผลรวมโควตา, ค่าขนาดใหญ่, ข้อมูลว่าง, ผู้ติดต่อ/Case, ประวัติบางส่วน และ Milestone
- `npx tsc --noEmit` และ ESLint ผ่านสำหรับ feature/routes/scripts ที่เกี่ยวข้อง
- `npm run build` ผ่าน
- `npm run check:dashboard:browser` — ผ่าน 19 สถานการณ์ ใช้ production build บน localhost พร้อม API fixture ในเบราว์เซอร์แยก ตรวจ login, ทุกโมดูล, การบันทึก/รีโหลด, ข้ามแท็บ, สิทธิ์แยกบัญชี, ธีมสว่าง/มืด และขนาดหน้าจอ 320/390/820 px
- หลังปรับสีปุ่มคืนค่าตั้งต้น ตรวจเฉพาะงานรอบนี้อีก 6 สถานการณ์ผ่าน โดยรันด้วย `node scripts/dashboard/check-browser.mjs --additions-only`
- ผลและภาพหน้าจออยู่ใน `frontend/output/playwright/dashboard/` ซึ่งเป็นผลการทดสอบ local ไม่ใช่หลักฐาน deployment หรือฐานข้อมูล production
