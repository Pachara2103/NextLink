# Dashboard: ส่วนที่เพิ่มตาม requirement

ปรับปรุงวันที่ 14 กันยายน 2569 ใน `Graph_RAG/frontend` บน branch สำหรับส่งรีวิว `codex/mock-dashboard-pr` ซึ่งแยกงาน Dashboard จาก `main` ล่าสุด

ขอบเขตงานคือ Dashboard mock ในเว็บ NextLink สำหรับเจ้าหน้าที่ ใช้ชุดข้อมูลสมมติและบันทึกในเบราว์เซอร์แยกตามบัญชี ยังไม่เชื่อมฐานข้อมูลธุรกิจจริงหรือ CRM API และไม่รวม Planner / NextPlus

## สิ่งที่ตรวจได้จากหน้าเว็บ

| หน้า | ส่วนที่เพิ่ม | วิธีทดลอง |
| --- | --- | --- |

| ทะเบียนบริษัท | รวมประวัติ MOU/วิชาเลือก/ฝึกงาน/สหกิจ/Capstone/Friday ตามปีและโมดูล; ผู้ติดต่อหลายคนพร้อมบทบาท ช่องทางติดต่อ และสถานะ; Case ย้อนหลัง | เปิด `/dashboard/companies` เลือกบริษัท แล้วแก้ผู้ติดต่อหรือเพิ่ม Case |

| Friday Activity | ผู้ประสานงานประจำกิจกรรมหลายคน; บริษัทลงนาม MOU แล้วที่ไม่พบกิจกรรมจัดเสร็จในชุดข้อมูล; รูปแบบ Hackathon/อื่น ๆ/ยังไม่ระบุ; วันที่ตอบแบบประเมินบริษัทเมื่อมีข้อมูล | เลือกผู้ประสานงานในรายละเอียดกิจกรรม และลองเปลี่ยนสถานะ MOU จากอีกแท็บ |

## ความหมายและข้อจำกัดของข้อมูล

- แหล่งอ้างอิงคือ requirement และเอกสารที่ตรวจไว้ใน parent workspace: `docs/audits/dashboard-requirements-2026-09-14/report.md` และ `docs/audits/dashboard-drive-recheck-2026-09-14/report.md` ไม่ได้นำรายชื่อนิสิตหรือข้อมูลติดต่อจริงจาก Drive มาใส่ใน fixture
- ทะเบียนบริษัทจับคู่โมดูลด้วยรหัสที่กำหนดชัดเจนสำหรับ fixture เท่านั้น บริษัทที่ชื่อคล้ายกันไม่ถูกควบรวมอัตโนมัติ ชื่อจากแต่ละชุดแสดงเป็น alias ตัวอย่าง
- ผู้ติดต่อในทะเบียนเป็นข้อมูลร่วมของ demo ส่วนชื่อผู้ประสานงานเดิมในแถว MOU/วิชาเลือก/โครงการยังเป็นข้อมูลประจำเอกสารหรือรายการนั้น ไม่ใช่การซิงก์กลับ CRM จริง
- Case เก็บวันที่เกิดเหตุ ปี/เทอม วันที่บันทึก ผู้บันทึก โมดูล รายละเอียด และสถานะ เรียง Case ล่าสุดตามวันที่เกิดเหตุ รองรับการบันทึกเหตุการณ์เก่าภายหลัง ประวัติในเบราว์เซอร์ยังไม่ใช่ audit log ที่ยืนยันจากเซิร์ฟเวอร์
- อันดับฝึกงานนับทุกอันดับบวกที่มีข้อมูล ไม่จำกัดแค่ 1–5 และแยกตำแหน่งด้วย Opening ID; ชื่อซ้ำที่ระบุไม่ได้จะไม่ถูกเดารวมกัน
- ตัวเลขรับแยกชั้นปี/รอบเป็นการแบ่งจำนวนใน fixture แบบไม่ซ้ำและผลรวมเท่าเดิม ไม่ใช่กฎโควตาจริง เมื่อกรองชั้นปี/รอบจะปิดการแก้ยอดรวม เพื่อไม่ให้บันทึกยอดบางส่วนทับยอดทั้งเทอม
- KPI นิสิตที่สมัครนับ `applicantRef` ไม่ซ้ำในบริษัท/ชั้นปี/รอบที่กรอง คนเดิมที่สมัครหลายรอบนับครั้งเดียว ไม่ใช้ ID ใบสมัครแทนรหัสนิสิตเมื่อรหัสหาย; จำนวนอันดับ 1 และแถบอันดับยังนับใบสมัคร/การเลือก
- KPI ตำแหน่งนับ Opening ID ของบริษัทตามตัวกรอง รวมตำแหน่งที่ยังไม่มีคนรับ ชุด mock ยังไม่มี eligibility ของตำแหน่งรายชั้นปี จึงไม่อ้างว่าจำนวนตำแหน่งเป็นโควตาสำหรับชั้นปีนั้น
- ผลรายนิสิตเก็บ studentRef, companyId, openingId, studyYear, round และ matched/accepted/started แบบ true/false/null พร้อมหมายเหตุ การเปลี่ยนขั้นหนึ่งไม่เปลี่ยนอีกขั้นอัตโนมัติ รวมคนไม่ซ้ำต่อขั้นและแสดงบริษัท/ตำแหน่งจากผลที่บันทึก ไม่เดาจากอันดับสมัคร
- ตัวเลขสามขั้นเป็นจำนวนจากรายการผลที่มีข้อมูล แต่ละขั้นมีคนซ้ำกันได้จึงนำยอดมารวมไม่ได้; null/ไม่มีรายการแสดงว่ายังไม่มีข้อมูล; เมื่อมีผลบางส่วนหรือไม่ทราบรหัสจะแสดง ≥ จำนวนคนที่ยืนยันได้
- เปลี่ยนชื่อยอด `InternshipPosition.accepted` เดิมเป็น “รับตามทะเบียน” เป็นยอดรวมที่รายงานไว้ แยกจากการตอบรับหรือเริ่มฝึกที่มีหลักฐานรายนิสิต ไม่ปรับยอดเก่าอัตโนมัติเมื่อแก้ผลรายนิสิต
- ผลรายนิสิตใน demo บันทึกแยกบัญชี ปี เทอม และฝึกงาน/สหกิจ รองรับสถานะยังไม่ทราบ การตรวจข้อมูลเสีย และป้องกันการเขียนทับเมื่ออีกแท็บแก้รายการเดียวกัน ยังไม่ใช่ข้อมูลจากฐานจริงและไม่มีการนำเข้ารายชื่อนิสิต
- Case ล่าสุดปรากฏในผลค้นหาทั้งตารางและการ์ดมือถือ อ่านทะเบียนบริษัทข้ามทุกปี/ทุกโมดูลโดยมีป้ายบอกขอบเขต วันที่ และสถานะ ถ้าอ่านข้อมูลไม่ได้จะไม่แสดงว่าไม่มี Case
- ผลประเมินฝึกงานเป็นนิสิตประเมินบริษัทในชุดสมมติ แยกจากคะแนนที่บริษัทประเมินนิสิต คำตอบว่างไม่เท่ากับศูนย์ ข้อมูลสหกิจยังต้องยืนยัน requirement และตัวอย่างเฉพาะโมดูลก่อนเชื่อมระบบจริง
- รายการ MOU ที่ไม่พบ Friday ใช้สถานะเอกสารเทอม 1/2569 และกิจกรรม `completed` ทุกเทอมใน fixture ปี 2566–2569 ไม่ใช้ตัวกรองรายการกิจกรรมมาจำกัดประวัติ และไม่สรุปหากข้อมูลบางส่วนอ่านไม่ได้ คำว่า “ไม่พบ” ไม่ใช่การรับรองว่าบริษัทไม่เคยเข้าร่วมในประวัติจริงทั้งหมด
- รูปแบบต้นทาง `Hackatron` จับคู่เป็น Hackathon โดยรักษาข้อความต้นทางไว้ ค่าว่างและรูปแบบที่ไม่รู้จักยังแยกจากกัน ผลประเมินบริษัทคงเป็นข้อความสามด้าน
- Milestone ต้องมีชื่อ วันที่จริงในปฏิทิน สถานะที่รองรับ และอ้างถึงทีมที่ยืนยันแล้ว การลบยังทิ้งประวัติก่อน–หลังไว้
- การเชื่อมบัญชีบริษัท/ผู้ติดต่อจริง การนำเข้าเอกสาร ผลประเมินจริง และการบันทึกลง Database v1 ยังเป็นขั้นตอนถัดไป

## ความครบเมื่อเทียบไฟล์ฝึกงาน

หน้า mock รองรับหัวข้อสถิติหลักใน `00 Note Internship` แต่ยังไม่ใช่การนำเข้าหรือเทียบยอดกับไฟล์จริงครบทุกคอลัมน์:

- `Master ฝึกงานทุกปี.xlsx` ยังมีรายละเอียดที่ไม่ได้เพิ่มในรอบนี้: วันเริ่ม–จบ/จำนวนวัน แผนกและลักษณะงาน พี่เลี้ยงประจำนิสิต TA/อาจารย์ เบี้ยเลี้ยงและสวัสดิการ ตลอดจนคะแนน Weekly/Bi-weekly รายงาน คลิปและเกรด
- คะแนนพี่เลี้ยงประเมินนิสิตและคะแนนความพึงพอใจที่นิสิตประเมินบริษัทเป็นคนละข้อมูล ต้องระบุคอลัมน์ต้นทางก่อนนำเข้าผลประเมินจริง
- การนำเข้าต้องเก็บ Student ID/Opening ID ปี/รอบ และอันดับทั้งสองฝั่ง; ตอนนี้กราฟอันดับใช้ความสนใจของนิสิต ส่วน Company Preference Rank และเวลาส่งยังไม่ถูกนำมาแสดง
- กติกาที่นั่งร่วมของชั้นปี 2–3 และสิทธิ์สมัครรายตำแหน่งต้องใช้ข้อมูลต้นทางที่ยืนยันแล้ว ไม่ใช้การแบ่งจำนวนของ mock เป็นโควตาจริง

## การตรวจสอบ

- `npm run check:dashboard` — 75 domain tests ครอบคลุมอันดับ 1–10, Opening ID ซ้ำชื่อ, ผลรวมโควตา, ค่าขนาดใหญ่, ข้อมูลว่าง, ผู้ติดต่อ/Case, ประวัติบางส่วน และ Milestone
- `npm run build` ผ่าน รวมการตรวจ TypeScript ของเว็บทั้งหมด
- `npm run lint` ผ่าน ไม่มี error; มี warning เดิม 13 จุดในหน้า login, shared layout, CRM และ service ของ `main`
- `npm run check:config` และ `npm run check:planner` ผ่าน โดยคงชุดทดสอบวิชาที่เพิ่มจาก `main` ล่าสุดไว้
- `npm run check:browser` — ผ่าน 26 สถานการณ์ของ Planner/CRM; ปรับ fixture ให้ส่งข้อมูล `/companies` คู่กับ `/line/groups` ตาม API ปัจจุบัน โดยคง assertions เดิม
- `npm run check:dashboard:browser` — ผ่าน 23 สถานการณ์ ใช้ production build บน localhost พร้อม API fixture ในเบราว์เซอร์แยก ตรวจ login, ทุกโมดูล, การบันทึก/รีโหลด, ข้ามแท็บ, สิทธิ์แยกบัญชี, ธีมสว่าง/มืด และขนาดหน้าจอ 320/390/820 px
- รอบนี้เพิ่ม browser checks สำหรับ KPI คนไม่ซ้ำ, สถานะรายนิสิตและการบันทึก, ข้อมูลเสีย, Case ข้ามแท็บ และหน้าจอผลฝึกงานสองธีม; ตรวจแยกบัญชีของผลรายนิสิตเพิ่มในชุดเดิม และรอเปลี่ยนช่วงการศึกษาเสร็จก่อนทดสอบค้นหา
- ผลและภาพหน้าจออยู่ใน `frontend/output/playwright/dashboard/` ซึ่งเป็นผลการทดสอบ local ไม่ใช่หลักฐาน deployment หรือฐานข้อมูล production
- CI ใน `frontend-integration.yml` รันทั้ง domain และ browser checks ของ Dashboard ร่วมกับชุดตรวจเดิม
